## Verified findings

### F1 — `+1` in MLSC proof depth check is wrong (Important)

**Location:** `src/rung/conditions.cpp:957`

```cpp
size_t total_leaves = total_rungs + total_relays + 1;  // line 957
size_t padded = 1;
while (padded < total_leaves) padded <<= 1;
size_t max_depth = 0;
for (size_t p = padded; p > 1; p >>= 1) ++max_depth;
if (n_proofs > max_depth) { ... }
```

vs the verifier at conditions.cpp:1174 and 1191:
```cpp
size_t total_leaves = proof.total_rungs + proof.total_relays;  // no +1
```

**Impact:** Deserialiser allows a Merkle path *one level deeper* than
the verifier expects when `total_rungs + total_relays` is a power of
2. Concretely:

| N+M | Deser max_depth | Verifier expected depth |
|----:|----------------:|------------------------:|
| 1   | 1               | 0                       |
| 2   | 2               | 1                       |
| 4   | 3               | 2                       |
| 8   | 4               | 3                       |

**Not a consensus split** — verifier rejects mismatched proofs (the
extra hash either changes the recomputed root or violates the layer
count), so both nodes still reject. But it IS a defence-in-depth gap
that lets an attacker waste 32 bytes per spend slipping past the
deser check, and the `+1` looks unjustified by the surrounding
geometry. `git blame` shows it dates from the initial commit
(`1490981274`), likely a leftover from a protocol version that
included a per-tx coil leaf (now folded into the rung leaf
template).

**Suggested fix:** Drop the `+1`. Verify against the existing test
corpus — single-leaf trees (`feature_rung_tx.py` has these) should
still pass with depth 0 max.

### F2 — Synthetic UTXO entry is never garbage-collected on the forward path (Important — already documented as deferred)

**Location:** `src/coins.cpp:130-152`

The synthetic root entry at `(txid, MLSC_ROOT_VOUT = 0xFFFFFFFF)` is
written in `AddCoins` but only removed in `DisconnectBlock`. The
in-code comment (lines 137-144) acknowledges this is a known gap:

```
KNOWN DESIGN GAP (audit #7 #6, v0.12 deferred): the synthetic entry
is only removed in DisconnectBlock — never on the forward path when
the last real MLSC output of the tx is spent. UTXO bloat is ~33 B +
Coin overhead per v4 tx, permanent past finality. ~9 MB/year at 100
v4 tx/block sustained.
```

**Impact on the BIP:** Q4 (MLSC chainstate) cites 8-12× chainstate
savings vs P2WPKH/P2TR. Those numbers assume the synthetic entries
are GC'd. With the gap unfixed:

- 9 MB/year of permanent chainstate growth at 100 v4 tx/block
- The "8-12× savings" claim is technically true at first-spend
  but degrades over time
- A reviewer who looks at the code will find this comment and it
  will undermine Q4's strongest pitch

**Two paths to close it:**

1. **Per-tx ref-count.** Add a uint16/uint32 live-output counter to
   the synthetic entry; decrement on each spend; delete the entry
   when the counter hits 0. Simple, in-place, no on-disk format
   change beyond the counter byte(s).
2. **Migrate to a separate index.** Move `conditions_root` storage
   out of the UTXO set into a dedicated leveldb index keyed by
   txid. Cleaner long-term but requires migration tooling and
   undermines the "chainstate" framing in Q4.

**Suggested action before mainnet:** Pick path 1 or path 2 and ship
it. The activation gate's component 7 (Independent implementation)
will trip on this — any alternative implementation will diverge on
when the entry disappears.

### F3 — `assumeutxo` does not work for v4 chains (Important — fail-closed in practice, but assumeutxo is effectively broken for v4)

**Location:** `src/validation.cpp:6128-6220` (`PopulateAndValidateSnapshot`),
`src/node/utxo_snapshot.cpp` (no MLSC-related code).

The snapshot loader emplaces coins via `EmplaceCoinInternalDANGER`
without any MLSC awareness. There's no synthetic-entry recovery, no
v4 awareness, no rejection of v4-bearing snapshots. The agent
flagged this as a critical silent-split risk; on close inspection
**the failure mode is loud, not silent**, but assumeutxo is
nonetheless broken for v4 chains.

**Why the failure is loud, not silent.** The existing anti-overflow
check at line 6189 rejects any outpoint with `n >=
std::numeric_limits<uint32_t>::max() == 0xFFFFFFFF`, which is exactly
`MLSC_ROOT_VOUT`. So if a snapshot serializer writes the synthetic
entries through the standard chainstate iterator, the loader rejects
the snapshot at "Bad snapshot data after deserializing N coins". That
fails closed.

**Why assumeutxo is still broken for v4.** Two independent paths:

1. **If the serializer writes synthetic entries** → loader rejects
   the snapshot. v4 chains cannot publish loadable snapshots.
2. **If the serializer skips synthetic entries** (or someone patches
   the loader to skip the `n == 0xFFFFFFFF` check) → loaded
   chainstate is missing the roots; subsequent v4 spend validation
   fails at `LadderBlockAccessor::FetchConditionsRoot`.

Either way, assumeutxo does not function for any chain that has
processed v4 transactions. This is a concrete consequence of the
"Stateless verifier obligation" the BIP names in §Security but
doesn't enforce in the snapshot path.

**Suggested action for the activation gate.** The cheapest fix
that satisfies the BIP's MUST-clause is option (b) from the previous
draft of this finding: explicit fail-closed rejection of any
snapshot whose `m_base_blockhash` is at or after the v4 activation
height. That's a one-line check in `PopulateAndValidateSnapshot`
before the loop. Doing it explicitly (rather than relying on the
anti-overflow guard tripping by accident) makes the contract
visible and gives reviewers a single line to point at.

The proper long-term fix is to extend the snapshot format with a
synthetic-entries section. That's a snapshot-format BIP in its own
right; not blocking for v4 activation if (b) ships first.

**Severity downgrade rationale:** The code does fail closed via the
existing anti-overflow check, so consensus safety holds. The
"silent split" framing the agent used is wrong. But the assumeutxo
feature genuinely doesn't work for v4 chains, and the BIP claims
it MUST work or be explicitly rejected. So Important, not Critical.

### F4 — DecodeHexTx error surfacing depends on caller passing non-null `error_out` (Important)

**Location:** `src/core_read.cpp:140-147, 160-162`

The recent commit `7761476d90` improved deser error reporting by
capturing `last_error` and surfacing exceptions via `error_out`. But
callers that pass `nullptr` (and there are several in the codebase,
particularly in the wallet path) silently drop the specific message
("qabi_block too large", "non-canonical ReadCompactSize") and
collapse to a generic "TX decode failed".

**Impact:** RPC users debugging malformed v4 txs get no
diagnostic. Not a consensus issue — purely DX, but it's the kind of
thing that turns into "Ladder Script's error messages are useless"
on a mailing list thread.

**Suggested fix:** Audit every `DecodeHexTx` call site. Either pass a
non-null `error_out` everywhere, or change the function to log to
stderr/log when `error_out` is null.

## Areas where agents flagged but I dismissed after verification

### Dismissed: `ReadCompactSize(ss, false)` "allows non-canonical encoding"

**Agent claim:** `serialize.cpp:206` calls `ReadCompactSize(ss, false)`
with `range_check=false`, supposedly allowing non-canonical encodings
to slip through.

**Verified:** The `range_check` flag in upstream Bitcoin's
`ReadCompactSize` (`src/serialize.h:330`) controls **only** the
`MAX_SIZE` check, not canonical-encoding rejection. Non-canonical
encodings are rejected unconditionally at lines 342, 348, 354 of
`serialize.h` (`throw std::ios_base::failure("non-canonical
ReadCompactSize()")`). The `false` flag is correct here — NUMERIC
field values can legitimately exceed `MAX_SIZE`, but the explicit
`> 0xFFFFFFFF` check at serialize.cpp:207 caps them at uint32.

### Dismissed: MULTISIG threshold uint32 truncation (sig.cpp:87, compound.cpp:292)

**Agent claim:** `*threshold_opt` is int64_t, cast to uint32_t
without upper-bound check, allowing K = 0x100000010 to truncate to 16
and bypass the multisig limit.

**Verified false positive.** NUMERIC fields are normalised to exactly
4 bytes LE at deser time (`serialize.cpp:213-217`); `ReadNumeric`
reads at most `field.data.size()` bytes and the wire invariant
guarantees this is 4. Max value is 0xFFFFFFFF, fits in uint32_t, no
truncation possible from any wire-format source. `ReadNumeric`
accepting up to 8 bytes is defence in depth that the wire format
never exercises.

### Dismissed: MULTISIG witness count `<` not `==` (sig.cpp:79)

**Agent claim:** `if (block.fields.size() < kCondCount)` allows extra
trailing fields to slip through (E-020-style embedding channel).

**Verified false positive.** The `< kCondCount` check at sig.cpp:79
is a sanity guard before subtraction; the **exact** witness count
match `witness_field_count != threshold * 3` is enforced at
`block_helpers.cpp:248` inside `VerifyMultisigInnerMerkle`. Each
triplet's per-position field types are checked at lines 273-277.
Extra fields cannot slip through.

### Dismissed: CScriptCheck cache pointer "lifetime violation"

**Agent claim:** The three cache pointers (`m_shared_tree_cache`,
`m_qabo_sig_cache`, `m_pq_batch_cache`) might be deallocated while
worker threads still hold references.

**Verified false positive.** `validation.h:392-394` declares them as
`std::shared_ptr<>` and they're moved into the `CScriptCheck`
instance via the constructor (line 397-398). The shared_ptr's
reference count keeps the cache alive for as long as the
`CScriptCheck` instance lives, and `CScriptCheck` itself is
move-constructible (line 402). Worker thread holds the
CScriptCheck which holds the shared_ptr which holds the cache. No
use-after-free.

## Spot-checked, no issues found

### Diff witness path (`serialize.cpp:600-685`)

Well-armoured. Verified the following defences are in place and
correct:
- Input index bounds-checked before cast (line 601)
- `MAX_DIFFS = MAX_FIELDS_PER_BLOCK × MAX_BLOCKS_PER_RUNG × MAX_RUNGS
  = 2048` cap before resize (line 609)
- Per-(rung,block,field) duplicate target rejection (D-1 fix; line
  639) — closes the no-op padding amplification
- Index range check `ri < MAX_RUNGS && bi < MAX_BLOCKS_PER_RUNG &&
  fi < MAX_FIELDS_PER_BLOCK` before tuple cast (line 628)
- Type whitelist for diff fields (PUBKEY/SIGNATURE/PREIMAGE/
  SCRIPT_BODY/SCHEME only — line 654-663). Closes the conditions-
  side type leak via diff overlay
- Per-witness PREIMAGE/SCRIPT_BODY cap enforced with explicit count
  (line 671-683) — closes F-3-class amplification

The 2048-diff cap is generous in absolute terms but the per-tx
PREIMAGE (2) and SCRIPT_BODY (1) caps are the real constraint on
embedded bytes. No finding here.

## Summary

**Critical actionable:** F3 (assumeutxo loader) — the BIP names this
as a MUST but the code doesn't enforce it. Cheap fix: fail-closed on
snapshot load when any v4 UTXO is present, until the snapshot format
is extended.

**Important actionable:**
- F1 (drop the `+1` at conditions.cpp:957)
- F2 (synthetic-entry GC — pick a path before mainnet; the BIP's Q4
  framing depends on it)
- F4 (DecodeHexTx error surfacing — audit all call sites)

**Not findings (agents over-reported):** ReadCompactSize false flag,
MULTISIG threshold truncation, MULTISIG witness count, CScriptCheck
cache lifetime — all verified-safe.

**State of the codebase as audited:** This is a *heavily*-audited
codebase (audits #1-#11 plus E-001..E-023). My pass found 4 things
worth landing pre-mainnet, all of which are either already
acknowledged in code (F2) or named in the BIP without code
enforcement (F3). The deep-crypto / merge / sighash / per-block
evaluator surfaces I checked are tight; the prior audit work shows.
The remaining risk surface is the boundary code (Core integration,
snapshot loaders, RPC validation) that the per-block focus of prior
audits didn't fully sweep.

**Recommendation for the activation gate's component 7 (Independent
implementation):** prioritise a libbitcoinkernel-style stateless
verifier. It will surface F3 immediately by failing on the first
snapshot load that includes a v4 UTXO; that's the highest-value
cross-implementation test.
